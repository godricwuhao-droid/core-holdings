# ADR-012: 生态人员下单「待审核」流程（pending 状态 + 商务改价确认）

## Status
Accepted（2026-10-19）

## Context
现状：生态人员（viewer）购物车结算**直接生效**——建项目 + 合同（`active`）+ 立即锁定数量，价格按产品挂牌价/明细单价自动计算，商务（editor/admin）事后只能走「项目编辑」改基本信息，**合同行价格无正式修改入口**（ADR-007 起合同结构不可改）。

业务诉求（2026-10-19）：生态人员负责加购下单 → 流程转给商务负责人 → 商务**修改单价和合同总价**后订单才正式生效。

与用户确认的 4 个决策点（2026-10-19，均取推荐项）：
1. **锁量时机**：提交即锁定（沿用「下单=锁定」防审核期超卖；驳回时释放）；
2. **适用范围**：~~仅生态人员购物车结算走待审核~~ → **修订（2026-10-19，用户拍板）**：**所有角色**（生态/商务/管理员）的**全部建单入口**（购物车结算/直接下单/手动建单）统一建 `pending` 走待审核——统一改价入口，任何人的单都能「接手→改价→确认」；
3. **操作人**：任意商务/管理员可确认/改价（`businessOwner` 仅作展示与路由提示，不做姓名绑定）；
4. **驳回处理**：项目置「已终止」+ 驳回原因留痕（生态人员仍可见记录与原因），不删除。

补充要求：商务可修改**单价（单价类产品）/ 合同金额（包量类产品）/ 合同总价（随合同行派生）**；**生态人员下单时可以不填金额**。

**二次决策（2026-10-19）——商务接手机制，取代决策点 3 的「任意商务可确认」**：生态人员下单**不指定**商务负责人；所有商务/管理员可见全部生态人员销售项目，**商务点「接手」认领**后 `businessOwner` 自动绑定**该商务账号**，此后仅接手账号（+管理员兜底）可改价/确认/驳回；支持**转交**（其他商务再次接手=改绑）。3 个边界均与用户确认：
5. **改价权限**：接手账号 + **管理员可越过**（普通商务仅接手人可操作；admin 可操作任意单，日志留痕实际操作人）；
6. **换人规则**：**支持转交**——其他商务可再次「接手」= 转交（businessOwner 改绑 + 日志留痕「X → Y」）；接手人**不可自行取消**（需转给别人）；`businessOwner` 必须关联**真实商务角色账号**（username），并支持按账号关联查询（列表筛选/展示）；
7. **接手范围**：**接手**仅 `pending` 订单（未认领 → 绑定本人）；`active`（进行中）订单仅可**转交**（已有负责人改绑）；`delivered/terminated` 终态不可接手/转交。

## Decision

### 1. 新增 `pending`（待审核）状态
- `projects.status` / `contracts.status` 均为 VARCHAR，新增取值 `pending`，**无 schema 迁移**；
- 状态机：`pending → active`（确认下单，商务）；`pending → terminated`（驳回，商务，必须填原因）。**修订（2026-10-19）**：新增 `pending → terminated`（**取消订单，下单生态人员本人**，项目级批量终止、释放锁定、记录留存）——下单人有权撤回自己的单；
- **守卫**：
  - 合同状态 API（`PATCH /contracts/{id}/status`）：合同 `pending` → 400「待审核合同请通过订单确认/驳回操作」（交付/终止/回退均不允许）；
  - 项目批量状态 API（`PATCH /projects/{id}/status`）：项目 `pending` → 400（同上，唯一出口是审核接口）；**修订（2026-10-19）例外**：下单生态人员（creator==自己）可 `terminated`（取消自己的待审核订单）;
  - 项目删除（`DELETE /projects/{id}`）：回滚链路把 `pending` 合同视同 `active`（释放 `it.locked` 明细锁定）；
  - 项目编辑约束「存在 delivered 合同不可编辑」不变，`pending` 项目允许改基本信息。
- **项目状态派生** `_derive_project_status` 增加规则：**全部合同 `pending` → 项目 `pending`**；其余规则（有 active→active、全 delivered→delivered、其余→terminated）不变。审核接口按项目整批迁移（该项目全部合同一起 confirm/reject），故不会出现 pending 与 active 混合的项目。

### 2. 建单入口
- **修订（2026-10-19）**：`_create_project_core` 默认 `initial_status="pending"`——**所有角色 × 所有入口**（`checkout` / `POST /projects` / `POST /sales/order`）统一建 `pending`（数量照常锁定、清空购物车）；原「viewer 分支 pending、editor/admin 立即 active」的角色分叉废除。
- 金额规则不变：viewer 的 amount 模式行可免填（回退挂牌价×数量取整）；商务/管理员下单金额仍必填。

### 3. 价格口径：登记单价 = 初始参考价，商务确认后实际价**同步回平台**（2026-10-19 用户确认）
- **产品挂牌价（`assets.salePrice`）定位**：登记时填写 = **初始参考价**（报价基准 + 下单占位价）；**商务确认下单后，实际价写回挂牌价**——平台各处的单价展示（产品列表/详情/购物车/概览）同步调整为最近一次成交价。
- 下单占位价：unit 模式 = 挂牌价 × 数量；amount 模式 = 合同金额（viewer 可免填，见下）。占位价始终读**当前挂牌价**，因此调价生效后后续新单自动按新价占位。
- 实际成交价在**商务审核时**确定：unit 行填**实际单价**、amount 行填**实际合同金额**（§4，确认时同步写回平台）。
- 口径说明：平台只有一个挂牌价，**不同客户的实际成交差异只落在各自合同行**；某客户成交价写回后，其他客户新单占位将采用该新价（业务接受的简化口径）。

### 3.1 生态人员免填金额（checkout 角色分叉）
- 现状：包量计价（amount 模式，ADR-008）产品结算时合同金额**必填**（`_validate_amount_yuan` 缺失/非整数 → 400）；
- 放宽：`checkout` 中 **viewer + amount 模式 + 行金额缺失/为 0** → 回退按参考价计价：**`amount = round(参考价 × qty)` 四舍五入取整元**（参考价可能非整数，如 Token 服务 33333.33，取整以满足 ADR-008 整数元约束）；viewer 显式填了金额仍按填写值（整数元校验保留）；
- **参考价未设置（`salePrice ≤ 0`）的 amount 模式产品**：viewer 免填不可行 → 400「产品《X》未登记参考单价，无法免填金额，请填写合同金额或先联系商务登记参考单价」（该分支下生态人员仍可在购物车手填金额下单）；
- **editor/admin 的结算/直接下单/手动建单**：金额必填规则不变（商务自己下单必须给价）；viewer 的直接下单（非购物车入口）同样不进 pending、金额必填不变。

### 4. 订单审核接口（新）
`POST /api/projects/{id}/review`（`require_editor`），单事务：

- 入参：`{ action: "confirm" | "reject", reason?: string, items?: [{ itemId, price?, amount? }] }`（`itemId` = `project_items.id`）；
- 前置校验：项目存在且 `status == pending`（否则 400「仅待审核项目可审核」）；`reject` 必须带非空 `reason`；
- **接手人守卫（§5.1）**：`businessOwner` 为空 → 400「该订单尚未被商务接手，请先接手后再操作」；操作人 ≠ `businessOwner` 且非 admin → 400「仅接手的商务负责人可调整该订单价格」（admin 兜底可越过，日志留痕实际操作人）；
- **confirm（确认下单，可带改价）**：
  - 改价口径（改**合同行** + **写回平台挂牌价**，§3）：
    - 单价类（unit 模式）行：传**实际单价** `price > 0` → `amount = price × qty` 重算（Decimal）；
    - 包量类（amount 模式）行：传**实际合同金额** `amount`（整数元 > 0，ADR-008 校验），派生参考单价（元/万Token，「约」）自动反算展示；
    - 遥感明细行（`itemId` 非空，ADR-011）：**不接受改价**（传了 → 400）——其金额权威 = `rs_items.price`，改明细价请走可售明细维护（`PUT /rs-items/{id}`）；
    - 未传改价的行保持原值；
    - **写回平台**（确认事务内）：改价行按 `assetId` 回写 `assets.salePrice`——unit 行写实际单价、amount 行写派生单价 `amount ÷ qty`（元/个，FLOAT 存储）；同一产品多行改价时**最后遍历到的行生效**；未改价的行不触发写回；写回同时记产品字段级变更日志（沿用现有 diff 机制）；
  - **数量审核时不可改**：改数量需重新校验/补锁库存，超出本次范围——需改数量 → 驳回重下（前端审核面板数量只读）；
  - **确认守卫**：确认后任一合同行 `amount ≤ 0` → 400「存在未定价明细，请先填写单价/合同金额」（防 0 元单生效，覆盖参考价未设的极端路径）；
  - 重算派生：合同 `contractAmount = Σ 行 amount` → `_recompute_project`（项目 `expectedAmount`/`contractAmount = Σ 合同`，即「项目总金额」随合同行价格间接变更，派生字段不直接录入，ADR-007 原则）；
  - 状态迁移：全部合同 `pending → active`、项目 `pending → active`；
  - 日志：操作日志「确认下单」（有改价时附行级 diff：产品名 单价/合同金额 旧→新）+ 审计「确认下单」；
- **reject（驳回）**：
  - 逐明细释放锁定（复用 `_apply_item_release`，仅 `it.locked`，cancel_release 流水带 contractId）；
  - 全部合同 `pending → terminated`（`contract.remark = "驳回：{reason}"` 留痕）、项目 `terminated`（`_recompute_project`）；
  - 日志：操作日志「驳回订单（{reason}）」+ 审计「驳回订单」；生态人员经 bootstrap 仍可见该项目及驳回原因（contract.remark）。

### 5. 权限与可见性
- 审核/接手接口 `require_editor`（admin + editor）；viewer 调 → 403（角色层拦截，无需归属校验——viewer 本就不可操作）；
- viewer 可见自己下单的 pending 项目（现有 `creator` 过滤天然覆盖），价格字段只读、无审核/接手入口；
- **`businessOwner` 语义变更（§5.1）**：由「展示用自由文本」升级为**商务角色真实账号（username）关联字段**——接手/转交动作写入，是审核改价的权限判定依据 + 列表按账号关联查询的键。

### 5.1 商务接手机制（2026-10-19 二次决策，取代原决策点 3；同日修订为**纯移交制**）
- **新接口 `POST /api/projects/{id}/claim`**（`require_editor`，可选 body `{"newOwner":"账号"}`）：
  - **无负责人**（pending/active 均可）：任意商务/管理员 → **接手**（绑定操作人账号）；
  - **已有负责人（移交）**：仅**当前负责人本人**可转交——body 必传 `newOwner`（目标须为启用中的商务/管理员账号，不能是自己）；
  - **admin 越过**：对他人负责的单据可直接接手（不传 newOwner）或转交给任意账号；
  - **非负责人的普通商务 → 400**「该订单由商务负责人「X」负责，仅其本人可转交（如需介入请联系 admin 处理）」——**不可抢单**（拉取式转交已废除，权责清晰、避免互相覆盖）；
  - `delivered`/`terminated` 终态 → 400「该订单已完成/已终止，不可接手或转交」；
  - 日志：操作日志「接手订单 / 转交订单」（target=project，detail 含 旧→新 账号）+ 审计「接手订单 / 转交订单」；
- **账号关联查询**：新接口 `GET /api/users/options`（任意登录用户）——返回 `role ∈ (editor, admin)` 且 enabled 的账号 `[{id, username, name, role}]`，供前端「商务负责人」筛选下拉与 username→姓名 展示映射；存量自由文本值（对不上账号）在筛选中归「未指派/历史数据」档；
- **`businessOwner` 写入口管控（2026-10-19 漏洞修复，含子 Agent 排查补漏）**：
  - `PUT /projects/{id}` **忽略** `businessOwner` 入参（原实现会直接写入 → 任意商务可编辑表单越权重设负责人，已废除）；前端编辑页「商务负责人」为只读展示，存量单据唯一变更途径是 claim 接手/转交。
  - 建单入口（checkout/sales/order/projects）可指定负责人但**必须通过 `_validate_business_owner` 校验**（存在/启用/editor+admin，与 claim 转交同口径）——原零校验，viewer 可传脏账号导致单据永久卡死 pending（排查修复）。
  - **pending 项目基本信息仅负责人（或 admin）可编辑**——非负责人 editor PUT → 400 `待审核项目仅商务负责人（或管理员）可编辑基本信息`；前端编辑页表单对 pending 非负责人整体禁用（`canEditForm`，与后端同口径）。
  - **confirm 前置守卫**：空项目（0 明细）与含未关联产品明细（pending_asset）的项目不可 confirm（400）——防 0 元空单生效、防悬挂明细锁死在不可交付状态（排查修复）。
- **审核守卫**（§4）：仅接手账号可 confirm/reject；admin 可越过任意单；未接手 → 400 提示先接手；
- **前端入口（纯移交制）**：项目列表「商务负责人」列（username 显示为 name(username)）+ 按账号筛选（含「未指派」）；接手/转交按钮三处统一（列表行/详情页顶栏/编辑页审核面板）：
  - 无主单（pending/active）→ 任意商务见「**接手**」（确认后绑定自己）；
  - 自己负责 → 「**转交**」→ `TransferDialog` 下拉选新负责人（启用商务账号列表，`GET /users/options`）；
  - 他人负责 → **仅 admin** 见「转交」（下拉多一个「接手给我」选项）；普通商务不显示按钮；
  - 编辑页审核面板底部：负责人/admin 在「确认下单/驳回」旁多出「转交」按钮。
- **审核入口权限（2026-10-19 最终版，多次修订收敛）**：pending 项目编辑/审核入口**仅负责人（或 admin 越过）可进入**，其余一律**禁止态**：
  - 列表行按钮：pending 统一显示「审核订单」（warning 橙），`canEditProject` 加 pending 门槛（owner===自己 或 admin），无权限者**禁用（灰）**+ tooltip「待审核项目仅商务负责人（或管理员）可进入，请先接手」；
  - 详情页顶栏：无权限者显示**禁用**的「审核订单」按钮（不再隐藏）；
  - 编辑页直连 URL：`noEditAccess`（pending + 非负责人商务）→ **只读提示页**（不渲染表单，防绕过入口按钮）；viewer 自己单的只读视图与 admin 越过不受影响。
  - **驳回/确认按钮仅负责人（或 admin）可见**——曾出现 `v-else` 误绑定「接手/转交」按钮条件导致非负责人也显示「驳回」的 bug，已修为独立 `v-if="canReviewEdit"`。

### 6. 前端
- `types.ts`：`ProjectStatus`/`ContractStatus` 联合类型加 `pending`；`PROJECT_STATUS`/`CONTRACT_STATUS` 标签映射加 `pending = 待审核`（warning 橙）；
- **项目列表**：状态筛选加「待审核」；商务/管理员对 pending 项目的行操作/抽屉底部出现「审核订单」→ 跳编辑页（审核模式）；生态人员仅看到「待审核」tag；
- **编辑页（create.vue 编辑态）**：`editProject.status === 'pending' && canWrite` 时显示**审核面板**——逐合同逐行可编辑价格（unit 行=单价输入，amount 行=合同金额输入，明细行只读带说明）+ 合同/项目合计实时重算 + 底部「确认下单」（primary）/「驳回」（danger，弹原因输入）；确认前校验与后端同口径；
- **项目详情页**：pending 合同不显示「交付/终止」按钮（状态 API 会 400，UI 先行禁用），状态 tag 正确渲染；
- **购物车（viewer 结算）**：amount 模式行金额输入改为**可选**（占位符「留空按挂牌价计价，商务可再调整」）；结算成功提示「下单成功，已提交商务确认」；editor/admin 提示不变。

### 7. 日志与审计
- 操作日志（logs）：动作「确认下单 / 驳回订单」（target=project，含改价 diff / 驳回原因）；
- 审计日志（audit_logs）：`actionType='project'`，action「确认下单 / 驳回订单」；
- 编号/流水：pending 订单锁定产生的 project_lock 流水、驳回的 cancel_release 流水均带 `contractId`（现有机制，无需改动）。

## Consequences
- **变容易**：生态人员订单的定价权集中到商务，业务上「先下单占量、商务再谈价」成为标准流程；生态人员下单门槛降低（可不填金额）；审核期数量已锁定，不存在「确认时无货」分支；`pending` 仅一个状态值，前端 tag/筛选/守卫改动面小。
- **变难**：`pending` 需要穿透所有状态感知点（派生/状态 API/删除回滚/抽屉按钮/详情按钮/筛选/tag 共 7 处守卫适配）；`checkout` 计价路径按角色分叉（viewer 金额可选）；新增一个「改价 + 派生重算 + 状态迁移」复合事务接口；编辑页新增审核模式分支。
- **可逆性**：**中**——回退 = 删除 review 接口 + checkout 一律建 active + 移除前端审核 UI；若库中已有 pending 数据，需先人工确认/驳回（或脚本批量确认）再回退。
