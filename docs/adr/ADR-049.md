# ADR-049：参考区间只约束下单下限；审核改价不受区间限制

- 状态：Accepted
- 日期：2026-10-29
- 部分取代：ADR-037 §3（区间校验分角色：viewer 只下限 / editor-admin 双向）
- 相关：ADR-018 §1（参考区间）、ADR-021（遥感明细区间）、ADR-048（金额精度 ≤6 位小数）

## 背景

参考区间（`assets.priceMin/priceMax`、`rs_items.priceMin/priceMax`）原本用于「限制折扣幅度」：
下单金额折算的单价必须落在 `[priceMin, priceMax]` 内，超限 400「单价超出该产品参考区间」。
ADR-037 §3 曾按角色放宽——viewer（生态人员）只校验下限，editor/admin 仍双向。

实际业务反馈两处阻塞：

1. **购物车下单**：生态人员按实际成交价填写金额，高于区间上限（如临时加价/涨价成交）会被 400 拦死，无法下单；
2. **商务审核改价**：审核环节本就是定价修正（可上调），若再受区间上限约束，改价与区间捆绑，业务无法落地。

## 决策

1. **购物车链路只校验下限**（所有角色一致）
   - 覆盖：`POST /cart`、`POST /cart/batch`（`_cart_add_inner`）、`PATCH /cart/{id}`（`patch_cart_item`）、
     `PUT /cart/{id}`（`set_cart_qty`）、`POST /cart/checkout`（`checkout` 分组校验 + 透传
     `_create_project_core(enforce_max=False)`）。
   - 规则：折算单价 < `priceMin` → 仍 400（原文案「单价超出该产品参考区间（…）」）；
     折算单价 > `priceMax` → **放行**；未设区间 = 不限制。
   - `enforce_max` 参数保留（`_check_discount_range` / `_check_unit_price_range` /
     `_normalize_contracts` / `_rs_row_amount` / `_item_pricing` / `_create_project_core`），
     购物车与结算固定传 `False`；路由层传入的 `viewer` 参数保留仅为签名兼容，不再影响区间口径。
   - 结算必须与购物车行同口径（两处都校验），否则会出现「购物车放行、结算 400」的割裂。

2. **审核改价不受区间限制**
   - `POST /projects/{id}/review`（`action=confirm`）的 `items[].price` / `items[].amount` 只校验
     「> 0」与「≤6 位小数」（ADR-048），**不调用** `_check_discount_range` /
     `_check_unit_price_range`，也不回写产品挂牌价（ADR-018 §4 不变）。
   - 该行为在本次之前即已如此（改价段只判 `price > 0`），本次把它明确写入契约并补上精度兜底，
     防止后续重构误加区间校验。

3. **商务手工建单（`POST /projects`）保持双向校验**
   - 不在本次需求范围内（用户明确范围为「购物车订单输入」与「商务审核改价」）。
   - 即 `_create_project_core` 的默认 `enforce_max=True` 仅剩该入口使用；如后续要放开，
     改一行调用参数即可，不涉及数据结构。

## 影响

| 层 | 变更 |
|---|---|
| 后端 `services.py` | `_cart_add_inner` 显式 `enforce_max=False`；`patch_cart_item` / `set_cart_qty` / `checkout` 的 `enforce_max = not viewer` → `False`；审核改价补单价 6 位小数校验；docstring 同步 |
| 前端 | 购物车顶部提示条去 `isViewer` 分支，改为「不得低于区间下限（上限不限制，可高于上限成交）」；产品/遥感明细表单区间说明改为「用于校验下限（上限不限制）」；购物车注释同步 |
| 数据结构 | 无变更，无迁移 |
| 行为变化 | 4 类入口的超上限金额由 400 变为可提交；下限 400 行为不变；审核改价不受区间影响（与本次前一致） |

## 风险与回滚

- 风险：金额高于区间上限的订单会进入「待审核」，由商务在审核环节把关（本身已是人工确认闸门）；
  平台侧不再用系统硬拦截替代人工定价判断。下限仍拦截，防止明显低价成交。
- 回滚：将 4 处 `enforce_max = False` 改回 `not viewer`、`_cart_add_inner` 去掉
  `enforce_max=False`，并恢复前端文案即可，无数据修复成本。

## 验证

副本库（`/tmp` 副本，不触碰生产）实测，取「智元机器人-G1」区间 `[3,036,767.00, 3,066,834.00] 元/套`：

- qty=1，金额 3,680,200.80（高于上限 20%）→ PATCH 通过并落库 ✅
- qty=1，金额 2,429,413.60（低于下限 20%）→ 400「单价超出该产品参考区间」✅
- qty=2，金额 7,360,401.60（单价超上限）→ PUT 通过 ✅
- `POST /cart/checkout` → 生成项目/合同/明细，行金额与合同金额均 = 3,680,200.80 ✅
- 审核改价单价 9,200,502.00（约 3 倍上限）→ 确认通过，`project_items.price/amount` 与合同金额同步 ✅
- 审核改价单价 1.1234567（7 位小数）→ 400「单价须最多保留 6 位小数」✅
