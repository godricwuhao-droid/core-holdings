# ADR-051: 权限体系升级（固定五角色 + 商务主管分配制 + 财务只读）

## Status
Accepted（2026-11-04，已实现 + QA 独立回归全绿：能力矩阵 35/35、数据隔离 18/18、分配链路 13/13、财务只读 12/12、回归 18/18、五角色 UI 实测）

## Context
现状（固定三角色，`security.py:15` 明写「不做动态权限表」）：
- 角色 `admin`/`editor`/`viewer` = 管理员/商务/生态；**无"财务"**；`User.role` 为 `String(20)`，改角色走 `tokenVersion+1`；JWT 不含 role（每请求查库）。
- 可见性只有 2 分支（`services.user_sees_project` / `Visibility`）：**admin/editor 看全部**、viewer 只看自己下单的；`businessOwner`（存 username 的字符串）**只管操作权、不管可见性**。
- 分配靠 `claim`（接手/转交，ADR-012）：无主单**任意商务**可接手、有主单仅负责人转交、admin 越过；生态下单 → `pending` + `businessOwner=""` → 商务手动接手 → 审核。

业务诉求（2026-11-04）：
1. **生态人员**：同现状——可下单、账号数据隔离。
2. **商务人员**：新增**商务主管**角色；下单后的销售项目都到商务主管；此时商务人员**看不到**未分配的项目；由商务主管**分配**给某商务；分配后**仅被分配商务 + 商务主管可见**。
3. **财务人员**：**只读**，仅查「产品/服务」；不能下单、不能编辑。

用户拍板的 4 个决策点（2026-11-04）：
- **Q1**：可有**多个**商务主管；新单进**未分配池**（`businessOwner` 留空），任一主管可见并可分配。
- **Q2**：**只收紧销售项目可见性**——主管/商务保留现有 产品/交付/公司主体/基础资料/交付物 编辑权；本次只改「销售项目可见性 + 分配链路 + 新增 2 角色」。
- **Q3**：商务主管**可审核**（confirm/reject，兜底处理人）。
- **Q4**：财务只读，**仅产品/服务**（含遥感明细/交付物/流程/日志），不看 销售项目/购物车/交付记录/公司主体/首页概览。

## Decision

### 0. 架构选择：静态集中式（不引入动态权限表）
- **理由**：小角色集（5 个、<~10）、业务稳定、内部低并发系统——静态（代码定义角色→能力 + 集中数据域函数）足够且更清晰（调研结论：动态权限表在权限点 >200 或频繁调整时才值得）。
- **可逆性优先**：保留「固定角色枚举」模型，把散落约 10 处的 `user.role==` 判断**收口**到 (a) 能力守卫（`security.py`）+ (b) 单一数据域函数（`user_sees_project`/`Visibility`）。全动态 RBAC（DB 权限表 + 配置 UI）留作日后升级，本次不做。
- **无 schema 迁移**：`User.role` 已是 `String(20)`、`Project.businessOwner` 已存在，新增角色取值 + 新规则即可。

### 1. 角色模型：固定 5 角色
| role | 展示 | 功能能力 | 销售项目数据域 |
|---|---|---|---|
| `admin` | 管理员 | 全部（含 用户管理/审计/删项目/公司主体） | 全部 |
| `supervisor` | 商务主管 | editor 全部业务写（产品/交付/主体/基础资料/交付物）+ 下单 + **查看所有销售项目** + **分配/改派** + **审核**（confirm/reject） | **全部**（未分配池 + 已分配） |
| `editor` | 商务 | editor 业务写（产品/交付/主体/基础资料/交付物）+ 下单 + 审核（仅名下） | **仅 `businessOwner==自己`** |
| `viewer` | 生态 | 下单 + 产品浏览（不变） | 仅 `creator==自己`（自己下的单，全状态） |
| `finance` | 财务 | **只读：仅产品/服务** | 无销售项目；产品/服务全量只读 |

- **能力 = 角色 → 权限点（能力守卫）**；**数据 = 角色 + 归属 → 行级域（`user_sees_project`/`Visibility`）**——两层正交（调研：功能权限 RBAC + 数据域行级过滤，且都须在**服务端**强制，前端藏按钮只是体验）。
- 需 admin 在「账号与审计」页**创建**主管/财务账号（运营动作，非迁移）。

### 2. 能力守卫（`security.py`，收口）
- `ROLES = ("admin","supervisor","editor","viewer","finance")`
- `EDITOR_ROLES = ("admin","supervisor","editor")`（业务写层：产品/交付/主体/基础资料/交付物 编辑 + 审核 + 接手/分配）
- `require_editor`：`role ∈ EDITOR_ROLES`
- `require_order`：**`role != "finance"`**（下单链路 admin/supervisor/editor/viewer；财务 403）
- **新增 `require_supervisor`**：`role ∈ ("admin","supervisor")`（分配/改派）
- `require_admin`：`role == "admin"`（不变）
- 产品**读**端点（`GET /assets` 等 `get_current_user`）：finance 允许（只读浏览产品/服务）。
- **财务排除**：finance 从 `require_order`（下单）与 `require_editor`（编辑/审核/交付/主体写）均排除 → 403。
- 注意：`supervisor` 纳入 `EDITOR_ROLES`（Q2：保留业务写权）；`_validate_business_owner` 的可操作者白名单纳入 supervisor。

### 3. 数据域（核心变更：`user_sees_project` + `Visibility`）
`user_sees_project(user, p)` 由 2 分支扩为 5 分支（**唯一可见性口径**，bootstrap + 全部分页端点共用）：
- `admin` → `True`
- `supervisor` → `True`
- `editor` → `p.businessOwner == user.username`
- `viewer` → `p.creator == user.username`（存量 creator 空回退 `rep in (user.name, username)`，不变）
- `finance` → `False`

`Visibility`/`build_visibility` 预计算按角色：
- `admin`/`supervisor` → `restricted=False`（全放行）。
- `editor` → `project_ids = {p.id | p.businessOwner==self}`（及其下 contract/outbound/flow/log/file）。
- `viewer` → `project_ids = {p.id | p.creator==self}`（不变）。
- `finance` → `project_ids = ∅`（**无** 销售项目/合同/交付/流水/日志/文件）。

**未分配池** = `businessOwner` 为空的项目：可见于 `admin` + `supervisor`（+ 下单生态 creator 本人，经 viewer 分支）。**普通 `editor` 不可见**。

**存量迁移（规则即迁移，无改数据）**：
- 现存 `businessOwner=""` 的项目 → 进入未分配池（商务将看不到，主管/admin 可分配）。
- 现存 `businessOwner=某商务` 的项目 → 该商务仍可见（+主管/admin）。
- ⚠️ 运营提示：上线后**存量未归属单需主管分配**，商务看不到；changelog 记注。

### 4. 分配链路（复用 `businessOwner` + `claim`）
`POST /projects/{id}/claim`（守卫 `require_editor`；语义扩展，**分配 = 主管身份下 claim with newOwner**）：
- **管理档（`role ∈ {admin, supervisor}`）——分配/改派**：对其**可见的任意项目**（=全部）可把 `businessOwner` 设为**任意启用中的 `editor`（商务）**：
  - body `{"newOwner":"商务username"}` → `businessOwner = newOwner`（分配未分配单 / 改派已分配单）；
  - 不传 `newOwner` 且当前无主 → 绑操作人自己（主管自己接手，edge，保留旧语义）。
- **商务档（`role == editor`）——保留 ADR-012 逻辑**：
  - 无主（`businessOwner=""`）且**自己可见**（如自己是 creator）→ 接手（绑自己）；
  - 有主且 `businessOwner==自己` → 转交（body 必传 `newOwner`，目标为启用 editor）；
  - 他人负责 → 400「该订单由「X」负责，如需改派请联系商务主管」（**不可抢单**）。
- `_validate_business_owner`：**分配/接手目标 = 启用中的 `editor`**；**可操作者 ∈ admin/supervisor/editor**。
- 状态：分配/改派**不改项目 status**（pending 仍 pending，由被分配商务或主管审核）。
- 日志/审计：分配=「分配订单（→ 商务X）」、改派=「改派订单（旧X → 新Y）」；复用 `record_audit` + `add_log`（target=project，含旧→新）。
- **审核守卫（ADR-012 §4）适配**：`confirm/reject` 操作人 = `businessOwner`（被分配商务）**或 admin/supervisor（越过，兜底）**。

### 5. 财务（finance）只读边界
- **可见（只读）**：产品/服务（`GET /assets`、rs-items、flows、logs、deliverables 读）——全量。
- **不可见/不可操作**：
  - 下单链路（cart/checkout/`POST /projects`/`status`/`withdraw`/`refill-cart`）→ `require_order` 排除 → 403。
  - 业务写（产品/交付/主体/基础资料/交付物）→ `require_editor` 排除 → 403。
  - 销售项目（list/detail/review/create/claim）→ `user_sees_project=∅`（bootstrap 过滤）+ `require_editor` 排除。
  - **公司主体（entities）**：`GET /entities` 对 finance **返回 `[]`**；bootstrap 对 finance **省略 `entities[]`**（财务不看主体）。写端点本就 `require_editor` → 403。
  - 交付（outbounds）/首页概览（dashboard）→ `Visibility` 无 outbound_ids → 空；前端路由不放行。
- **前端**：finance 菜单 = 仅「产品及服务」（各板块 + 详情）；无 销售管理/购物车/交付/公司主体/首页/设置。

### 6. `/users/options`（分配下拉数据源）
- 保持 `GET /users/options` 返回 `role ∈ (editor, admin)` 且 enabled（供转交/展示映射）。
- **分配下拉 = 前端过滤出 `role=='editor'` 的子集**（不改接口、不加参数，前端过滤）——契约：主管「分配」下拉只列**商务（editor）**账号。

### 7. 前端
- **`auth.ts`**：`Role` 联合类型加 `supervisor`/`finance`；`ROLE_LABELS` 加 `supervisor=商务主管`/`finance=财务`；`canWrite = role ∈ (admin,supervisor,editor)`（finance 变 false）；新增 `isSupervisor`/`isFinance`；角色 tag 颜色。
- **`router`**：新增 `financeAllowedPath`（仅 `/assets/*` 板块 + 详情；其余 → 提示回 `/assets/{板块}`）；`supervisor` 路由权限 = 与 editor/admin 一致（可进 sales/delivery/settings 读写）。
- **`MainLayout.vue`**：菜单按角色显隐——`finance` 仅「产品及服务」；`supervisor` 显示销售管理（含未分配入口/筛选）；各角色 tag。
- **`projects/index.vue`**：
  - `editor`：列表**已由后端只返回名下**（前端无需再过滤，负责人筛选保留即可）；
  - `supervisor`：新增**「分配」按钮**（列表行 + 详情 + 审核页，复用 `TransferDialog`，options 过滤 editor），可对未分配/已分配单分配/改派；**「未分配（未指派）」筛选**作为派单入口（复用现有负责人筛选的「未指派」档）。
- **`review.vue`**：`supervisor` 可审核（confirm/reject）+ 可分配/改派（Q3 兜底）。
- **`users.vue`**：`ROLE_OPTIONS` 加 `supervisor`/`finance`（建号/改角色下拉含 5 角色）。
- 遵循 `core-holdings-ui`（主蓝 #1769D4、状态 tag、按钮规格）。

### 8. 不变量（回归护栏，QA 必测）
- 生态（viewer）行为**完全不变**：下单、看自己单、数据隔离、撤销/终止/重下。
- admin 全权**不变**。
- 产品/交付/主体/基础资料/交付物 的编辑权：admin/supervisor/editor **不变**（财务本就不能编辑）。
- ADR-012 接手/转交/审核 逻辑保留，仅**叠加** supervisor 分配分支 + 可见性收紧；ADR-050 审核改价/改数量不受影响（审核人 = 被分配商务或主管，逻辑同）。

## 接口契约（前后端对接）
| 项 | 契约 |
|---|---|
| 角色取值 | `role ∈ {admin, supervisor, editor, viewer, finance}`（`User.role` String，无迁移） |
| 分配 | 复用 `POST /projects/{id}/claim`，body `{"newOwner":"商务username"}`；主管/admin 可对任意可见项目设 businessOwner（分配/改派）；商务按 ADR-012 规则 |
| 分配下拉 | `GET /users/options`（不变，返回 editor+admin）；前端过滤 `role=='editor'` 作为可分配商务 |
| 可见性 | 项目列表/详情/审核/交付/文件 均走 `user_sees_project`/`Visibility`（editor 仅名下、supervisor/admin 全部、viewer 仅自己、finance 无） |
| 财务 | finance：产品/服务只读（`get_current_user` 读端点放行）；下单/编辑/销售/主体 → 403；`GET /entities`→`[]`、bootstrap 省略 entities |
| 审核守卫 | confirm/reject：`businessOwner`（被分配商务）或 admin/supervisor（越过）；未分配（无 owner）→ 400「请先由商务主管分配」 |

## Consequences
- **变容易**：销售项目归属清晰（主管分配制、商务只看名下，降噪）；主管统一派单入口（未分配池）便于督办；财务可安全只读查产品；能力/数据域收口到守卫 + 单一函数，后续加角色/改域改动集中。
- **变难**：`user_sees_project` 2→5 分支 + `Visibility` 按角色预计算；`claim` 加 supervisor 分配分支；前端角色 3→5（类型/标签/路由/菜单/页面/users 下拉）；审核守卫加 supervisor 越过；存量未归属单需主管分配（运营成本）。
- **可逆性：中**——回退 = 角色收回 3 个 + `user_sees_project` 回 editor 全量 + 移除 supervisor 分配分支与财务排除 + 前端撤 2 角色。存量 `businessOwner` 保留（回退后 editor 全量可见，行为回到现状）。**无 schema 迁移**。
- **未决/未来**：多主管是否需要「分管段」（主管 A 只看 A 段）——本次默认**所有主管看全部**（管理/兜底层，最简且可逆），如需按段再扩展数据域。
