# ADR-015: 手动补录交付不触碰 lockedQty，仅增加 shippedQty，并补齐归属校验

## Status
Accepted（2026-10-20）

## Context
BUG-20261020-#2/#9/#13a：`create_outbound`（手动补录交付）在 `mode != "history"` 时无条件执行 `lockedQty = max(0, lockedQty - qty)` 且 `shippedQty += qty`。补录并不对应任何订单明细、也未释放过对应的锁，却会：
- 偷减其他订单持有的锁定（`lockedQty` 是所有订单锁定的共享池）；
- 使可售校验（`quantity - lockedQty - shippedQty`）基于被偷减后的数值放行，跨订单场景下累计承诺可超总量（超卖）；
- 撤销补录后 `lockedQty` 不还原，可售凭空增加。

同时 `create_outbound` 缺少项目状态校验（pending 可挂交付）、产品与项目归属校验、遥感父产品拦截，且 `OutboundInput.qty` 允许 0。

## Decision
1. 手动交付（`mode != "history"` 且无 contract 关联）只执行 `shippedQty += qty`，**不得触碰 `lockedQty`**；保留并前移可售校验 `qty <= quantity - lockedQty - shippedQty`（基于未改动的 lockedQty 计算）。
2. 服务层校验 `qty > 0`（schemas 的 `ge=0` 保留，服务层拒绝 0）。
3. 归属校验：若传了 `projectId`，要求 a) 项目状态非 `terminated` 且非 `pending`（待审核不可交付）；b) 该 `assetId` 必须存在于该项目明细中，否则 400。
4. 拦截遥感父产品：`asset.type == '遥感数据'` 的容器不允许直接交付（只能对其明细交付）。
5. 前端补录弹窗：移除无效的"经办人"输入框（后端本就不采信 `data.operator`）；项目下拉排除 `pending` 与 `terminated`。
6. 「对具体订单明细交付」的能力（落到 `ProjectItem` 并走 `_apply_item_delivery`）不在本次范围，留待后续 ADR 演进。

## Consequences
- 变容易：手动交付与订单交付的库存口径各自守恒（订单交付=锁定转已交付；手动交付=纯减可售）；撤销路径对称、不产生漂移。
- 变难：已有依赖"补录自动释放锁定"习惯的操作流程需适应（当前库 outbounds=0，无存量数据需迁移）。
- 可逆性：高。仅改单函数内的库存变更行 + 新增前置校验，回滚即恢复原逻辑。
