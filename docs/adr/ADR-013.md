# ADR-013: 销售记录（一资产一条记录 + 多主体 + 「合同」文案改名）

## Status
Accepted（2026-10-19 用户确认）

## Context
现状（ADR-007）：购物车结算按**行级客户**分组，每客户一份「合同」，且**合同内强制同一产品主体**（`_create_project_core` / `_order_core` / `checkout` 三处校验）。业务上同一客户一次采购多家主体（供货公司）的产品是常态（实测：客户「优」同买 遥感数据-2026（蜂云时代）+ 城市部品（四川蜂云星座）+ 青牛大数据（安徽天枢智算）→ 结算 400「主体不一致，请拆分」）。

业务澄清（2026-10-19）：这些单据不是法律意义上的合同，本质是**销售流水单据**——每个资产（产品）的销售都是独立的，应称为「销售记录」而非「合同」；一单可以包含不同主体的资产。

与用户确认的 2 个决策点：
1. **记录粒度 = 一个资产一条记录**：购物车里每个产品行 = 一条独立销售记录（各自主体/数量/单价/金额），同一项目下多条并列；遥感明细的多行勾选仍归父产品同一条记录；
2. **改名范围 = 仅界面文案**：界面文案「合同」→「销售记录」（状态 tag、按钮、提示、报错、日志）；**代码/表名/接口路径不变**（`contracts` 表、`/contracts/` 路由、`contractAmount` 字段保留），编号 `HT-xxxx` 前缀不变，存量数据零迁移。

## Decision

### 1. 记录粒度：一资产一条记录
- **购物车结算**：分组键从 `customer` 改为 **`assetId`**（遥感明细行按父产品归组）——每个产品行一条记录，`customer` 取该行行级客户；同一客户的不同产品 → 同项目下多条记录；
- **直接下单**（`_order_core`）：同规则按资产拆分（原「单合同语义」废弃），明细行归父产品；
- **手动建单**（`POST /projects`）：保留商务自由组织结构（可多行/混合主体成一条），仅移除同主体校验——标准路径（购物车/直接下单）自动按资产拆分，手动路径不强制；
- 遥感明细：一条记录 = 父产品 + N 条明细行（现状结构不变，只是每条记录只含一个父产品）。

### 2. 多主体
- 三处「合同内同主体」校验**全部移除**（购物车/直接下单/建单核心）；
- 记录 `subject` 派生：**各行主体全一致 → 该值；混合 → 空串**（语义=多主体，前端展示「多主体」，不存逗号拼接）；
- 项目级 `customer`/`subject` 派生规则不变（多条记录 → 空串，前端显示「N 位客户」）；
- **锁定/交付/审核/驳回**均为行级逻辑，与主体无关，零改动；审核改价按 `assetId` 写回挂牌价，天然兼容；
- 业务语义：多主体记录在现实中通常是框架协议+多主体附件或由商务代签——系统只如实记录每行归属，签约文书线下处理（系统不实现签约）。

### 3. 文案改名（仅界面，代码不动）
- 「合同」→「**销售记录**」：状态 tag、列表列（关联合同→销售记录）、抽屉/详情卡片、审核面板（按合同分区→按记录分区）、按钮（交付合同→交付）、报错与操作日志（「合同不存在」→「销售记录不存在」等）；
- 「合同金额」→「**销售金额**」（列表列/合计/amount 模式输入框标签）；
- 记录编号 `HT-xxxx` 前缀与展示不变（「编号」标签）；「签约主体」文案保留（指产品归属的供货/签约公司）；
- 代码标识（`contracts` 表、`/api/contracts/` 路由、`contractAmount` 字段、`Contract` 类）全部保留，零迁移；存量数据（多行合同）原样展示为「销售记录」。

## Consequences
- **变容易**：同客户多主体产品一次结算不再被拦；单据粒度细化到资产，交付/终止/审核以单资产为单位更清晰；「销售记录」定位轻，不再背负合同级法律语义；
- **变难**：一次下单的记录数变多（N 个产品 → N 条 HT 编号）；手动建单与自动路径的记录结构不再同构（手动可多行/混合，自动恒单资产）；文案替换面大（前端 6+ 页面 + 后端用户可见字符串），需防漏改/误改代码标识；
- **可逆性**：高——校验与分组键回滚即恢复旧行为（HT 编号/表结构未动，存量数据兼容）；文案回滚为纯字符串替换。
