# ADR-031: 启动迁移治理（禁止启动期清理业务数据）

## Status
Accepted（2026-10-22，来源：`business-logic-bugs-20261022.md` BUG-01）

## Context
`backend/main.py` 的 `_ensure_migration()` 在**每次进程启动**时执行，其中第 17 条把"ADR-024 上线时一次性清空存量交付物"实现为「表非空即 `DELETE`」：

```python
if "asset_deliverables" in table_names:
    n = conn.execute(text("SELECT COUNT(*) FROM asset_deliverables")).scalar()
    if n:
        conn.execute(text("DELETE FROM asset_deliverables"))
```

后果（已实证）：`asset_deliverables` 当前 0 行，但审计日志有 13 条交付物操作记录、28 个产品仍在 → 历史录入的交付物在每次重启（含 `--reload` 热重载）中被静默删除，附件仍留在 `uploads/` 但引用丢失。

根因是**迁移框架缺失**：没有"已执行"标记，只能靠"空表跳过"当作幂等，而业务数据永远会有新行，于是"幂等条件"与"业务状态"耦合。

## Decision
1. 新增 `schema_migrations(name PRIMARY KEY, appliedAt)`；所有**数据类**一次性动作必须写入标记，执行前查标记。
2. **启动期只允许结构迁移**（`CREATE TABLE/INDEX`、`ALTER TABLE ADD COLUMN`、幂等 `DROP` 废弃表）；**禁止**在启动期对业务表执行 `DELETE/UPDATE`。
3. 本次立即移除第 17 条 `DELETE`，并写入标记 `ADR024_cleanup_done`（表示"历史清理已完成/不再执行"）。
4. 后续确需数据修复，改为 `backend/scripts/` 下的显式脚本，由人工执行并在 changelog 记录。
5. 迁移脚本必须满足：同库重复执行无副作用；失败不阻断启动（除结构缺失）；每条打印 `[migration] ...` 可追溯。

## Consequences
- **变容易**：重启不再有数据风险；迁移可审计（谁在何时应用了哪条）；新迁移不必再设计"靠业务状态判断"的伪幂等。
- **变难**：一次性数据清理多了一步人工执行；历史库里"已经删掉"的交付物**无法恢复**（附件仍在 `uploads/`，可人工按审计日志重建）。
- **可逆性**：**高**。`schema_migrations` 是纯增量表；回退只需恢复旧启动逻辑（不建议）。
