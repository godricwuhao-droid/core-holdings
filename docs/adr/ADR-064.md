# ADR-064: 销售项目新增「待分配」状态（商务主管分配流程显性化）

## Status
Accepted（2026-11-10，后端+前端已实现 + 自测/Architect 代码核对 + 端到端冒烟通过：**后端** `_derive_project_status` 两个 pending 分支走 `_pending_or_pending_assign`(businessOwner 空→`pending_assign`/否则 `pending`，active/delivering/delivered/terminated 不受影响)、`claim_project` 分配/改派/接手/转交成功后补 `_recompute_project`(2482-2486，`pending_assign↔pending` 自动流转)、`withdraw` 放行 `pending_assign`、`api.py` 排序 rank 前置(pending_assign=0)、`main.py` 幂等回填迁移(本次 0 条、标记化只跑一次)；**review 守卫/`user_sees_project`/claim 端点不变**。前端 `types.ts` 加 `pending_assign`(label 待分配/tag `info` 中性色)、`index.vue`+`detail.vue` 按钮可见性审计(`canAssignRow`/`canWithdrawRow`/`canEditProject` 补 `pending_assign`：主管/管理员显「分配/改派」、不显「审核订单」、下单人显「撤销」、编辑限 admin/supervisor)、`outbound` 排除可交付、`api/index.ts` 过滤核对无漏、`review.vue` 天然不可审；**端到端冒烟**：建单未分配→`pending_assign`、review→400、claim→`pending`+owner；自测含 editor 不可见(数据域)、分配→待审核、撤销、筛选下拉、排序、全状态回归，vue-tsc 0）

## Context
用户要求：销售项目新增一个**针对商务主管（supervisor）角色的流程状态「待分配」**。
现状（code-explorer 已摸清，行号以实际为准）：
- 项目 `status` 是**派生字段**（由名下合同状态推导，ADR-007），5 值 `pending/active/delivering/delivered/terminated`；`Project.status` 为**物化列**，经 `_recompute_project`（`services.py:2177`）在合同变更后刷新。
- **分配机制已存在**（ADR-051）：`Project.businessOwner`（`models.py:80`，存商务 username）+ `POST /projects/{id}/claim`（`api.py:592`，分配/改派/接手/转交四动作）+ "未分配池"（`businessOwner` 空，筛选值 `__none__`）。
- **"未分配"目前只是 `pending + businessOwner 空` 的隐藏组合，不是独立状态**——列表上不显示成独立状态、筛选里叫"未指派/历史数据"。
- **未分配时本就不可审核**：review 守卫 `businessOwner` 空 → 400「该订单尚未分配，请先由商务主管分配」（`services.py:2511`）。
- 角色：`supervisor`（商务主管，做分配/改派，`require_supervisor` 层）≠ `editor`（商务人员，做审核）。

用户已确认（2026-11-10）：
1. 「商务管理」= **supervisor（商务主管）**。
2. 「待分配」= **下单后、分配负责人前**（待审核的前置）——即把现有"未分配池"显性化。
3. **可见/操作**：**仅 supervisor/admin 可见 + 可分配/改派**（editor 不可见待分配池，与现有 editor 数据域一致）；**撤单保持现状**（下单人/admin 可撤 → terminated）。

## Decision
**「待分配」= 派生子态 `pending_assign`**：当项目合同含 `pending` 且 `businessOwner` 为空时，派生 `status = pending_assign`（待分配）；supervisor/admin 分配（设 `businessOwner`）后经重算回落为 `pending`（待审核）。

**两方案对比**：
- **A（选中）物化派生 + 一次性回填**：改 `_derive_project_status` 引入 `businessOwner`，`status` 列存 `pending_assign`，claim 后重算 + 启动回填。**与现有"物化派生状态"架构一致**；查询/过滤/守卫都直接作用在 `status` 列上，简单一致。代价：`businessOwner` 每次变更需触发重算、多处 `status==` 硬编码需审计。
- **B（弃用）读取时计算**：`status` 列保持 `pending`，仅在 API 响应把 `(pending && !businessOwner)` 映射成 `pending_assign`。省掉回填与重算，但**存储列与 API 状态背离**（后端 `p.status==pending` 逻辑与前端所见不一致）、过滤 `待分配`/`待审核` 都需叠加 `businessOwner` 条件、后续维护易踩坑。

**落法（方案 A）**：
1. **后端 `_derive_project_status`（`services.py:2134-2174`）**：新增分支——合同含 `pending` 且 `p.businessOwner` 为空 → 返回 `pending_assign`；否则维持原逻辑。函数需读 `p.businessOwner`（当前只读 contracts）。
2. **`businessOwner` 变更触发重算**：`claim_project`（`services.py:2417-2467`，分配/改派/接手/转交）成功后调用 `_recompute_project(p)`，使 `status` 在 `pending_assign ↔ pending` 自动同步（当前 claim 不改 status，需补）；withdraw 解绑路径同理（withdraw→terminated，无碍）。
3. **一次性回填**：启动时（`main.py` 的 `SchemaMigration` 标记机制，`models.py:364`）对存量项目跑一遍 `_recompute_project`，把 `status='pending' AND businessOwner=''` 回填为 `pending_assign`（**零手动迁移**，与 ADR-051 未分配池口径一致）。
4. **守卫核对**（`pending_assign` 放行/拦截）：
   - review（`services.py:2506-2516`）：`仅 pending 可审` → `pending_assign` 天然不可审（`!= pending` + businessOwner 空 400 双保险），**不改**。
   - withdraw（`services.py:1558` 附近）：`仅 pending 可撤` → 改 `status in ("pending","pending_assign")`（**待分配也可撤**，保持现状）。
   - 合同守卫（`2294-2303`）、claim 终态判断（`2433`）：核对 `pending_assign` 放行语义。
   - 排序 rank（`api.py:329-338`）：加 `pending_assign` 档位，**置于 `pending` 之前**（最需处理排最前）。
   - 建单入口（`services.py:1853-1868`）：新单 contract=pending + businessOwner 空 → 派生即 `pending_assign`（自动）。
5. **可见性**：`user_sees_project`（`services.py:132-152`）不变——editor 按 `businessOwner==自己` 过滤，天然看不到待分配单；supervisor/admin 全见。**不改**。
6. **前端**：
   - `types.ts`：`ProjectStatus` 联合 + `PROJECT_STATUS` 加 `pending_assign = { label:'待分配', tag:<颜色> }`（建议 `info` 灰蓝，与 pending 的黄区分；遵循 core-holdings-ui，可调）。`PROJECT_FLOW`（active/delivering/delivered）不含前置态，**不动**。
   - `index.vue`：状态筛选下拉（`517-519` 遍历 PROJECT_STATUS）+ 状态列 tag（`571-579`）**自动生效**；按钮可见性逐一核对——`pending_assign` 行：supervisor/admin 显「分配/改派」、**不显「审核订单」**、下单人显「撤销」；`canReviewRow/goEdit/canWithdrawRow/canAssignRow/canEditProject`（`73/270/133/123/296`）按 `pending_assign` 核对。
   - `review.vue`（`isPending:57` / `canReview:241`）、`detail.vue`（`canReview:55`）：`pending_assign` 不可进审核（审核按钮由 `status==pending` 控制，自然不显）。
   - `outbound/index.vue:107`：待分配同样排除在可交付项目外；`api/index.ts:433-449` bootstrap 本地过滤含 `pending_assign`。
   - 分配交互复用现有 `TransferDialog` assign 模式 + `claimProject`（`index.vue:607`），**无新组件**。

**接口契约（前后端）**：`Project.status` 取值新增 `pending_assign`（中文"待分配"）；`GET /projects` 响应 `status` 可为 `pending_assign`；`GET /projects?status=pending_assign` 过滤未分配 pending；`POST /projects/{id}/claim` **不变**（分配后该项目 `status → pending`）。无新端点。

## Consequences
- 易：隐性的"未分配"显性化为可见状态，商务主管有明确处理队列；派生+回填零手动迁移；分配后自动流转、复用既有 claim/TransferDialog。
- 难/代价：`status` 派生源从"仅合同"扩展到"合同 + businessOwner"（正交字段引入派生）；`businessOwner` 每次变更需触发重算；`pending` 相关守卫多处需逐一核对放行/拦截（漏改会误拦审核/撤单）；新增物化枚举值，前后端多处硬编码 `status==` 需审计。
- 可逆性：**中**——逻辑可逆（去掉派生分支 + 反向回填），但涉及多处守卫与一次回填，回退需回归测试。
