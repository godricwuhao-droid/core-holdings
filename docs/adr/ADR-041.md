# ADR-041: 销售项目终止态细分展示 + 抽屉「流转过程」

## Status
Accepted（2026-10-22，业务要求：撤销/驳回都显示「已终止」不可区分；抽屉需看流转过程与撤销/驳回原因）

## Context

1. **三种终止在数据上是同一个 `status`**：
   - 撤销（ADR-026）：`POST /projects/{id}/withdraw` → 项目 `terminated` + `cartRefilled=1` + 合同 remark「撤销：{原因}」
   - 驳回（ADR-012）：`POST /projects/{id}/review` action=reject → 项目 `terminated` + 合同 remark「…｜驳回：{原因}」
   - 普通终止（ADR-032）：`PATCH /projects/{id}/status` → 项目 `terminated`，无前缀
   三者业务含义完全不同（撤销=本人反悔、驳回=商务否决、终止=作废生效单），但列表/抽屉/详情页一律显示「已终止」，生态人员看不出被驳回还是自己撤销的。
2. **原因文本已经存在，但不聚合**：原因分散在 `contracts.remark`（前缀「撤销：」/「驳回：」）与 `logs.detail`（「…原因：X」「…订单已驳回：X（锁定已释放）」）。项目层级无单一「结论 + 原因」字段。
3. **流转事件已在 OpLog 里，但前端拿不到外键**：`logs` 表有 `projectId`，`add_log` 所有项目级动作（新增项目/接手/转交/确认下单/驳回/撤销/状态变更/重新提交/编辑/删除）均写入；`Visibility.log_visible` 也已按 `projectId` 为 viewer 过滤。**唯一缺口：`schemas.LogOut` 未输出 `projectId`**，前端只能按 `targetName`（项目名）匹配 —— 重名/改名即串台。

## Decision

### 1. 终止态三分：**只做展示，不动状态机**
新增纯函数 `projectOutcome(p, logs)` → `'revoked' | 'rejected' | 'terminated'`，判定链（先精确、后兜底）：
1. `status !== 'terminated'` → 按原 status 渲染（不介入）；
2. `logs` 中存在 `projectId === p.id && action === '撤销订单'` → **已撤销**；
3. 存在 `projectId === p.id && action === '驳回订单'` → **已驳回**；
4. 兜底（无日志的存量单）：任一合同 `remark` 以「撤销：」开头/含「撤销：」→ 已撤销；含「驳回：」→ 已驳回；
5. 都不满足 → **已终止**。

**不做的**：
- **不新增 `Project.status` 枚举值**（否则状态机、`PATCH` 守卫、派生逻辑、`statusFilter` 全要改，且后端仍只有一个 terminated 语义）；
- **不改筛选下拉**（仍 5 项真实状态「已终止」包含撤销/驳回）——筛选口径必须与后端一致，否则前端筛「已撤销」会返回空/少数据；
- 不改任何接口返回结构与业务逻辑。

### 2. 抽屉「流转过程」：复用 bootstrap 日志，**不新增端点**
- 后端：`schemas.LogOut` **加性**增加 `projectId: int | None = None`（visibility 已按该字段过滤，无行为变更）。
- 前端：`types.OpLog` 加 `projectId?: number | null`；抽屉新增「流转过程」区块，`db.logs.filter(l => l.projectId === p.id)` 按 `time`/`id` 升序渲染 `el-timeline`，每条 = `time · operator` + `action`（色点）+ `detail`。
- 原因单独提取并高亮：撤销事件 `原因：(.+?)(；|$)`、驳回事件 `已驳回：(.+?)（`；提取失败则回退 `contracts.remark` 的「撤销：/驳回：」后缀。展示为事件卡片下一行「原因：…」。

### 3. 一致性范围
`projectOutcome` 同时用于：列表「项目状态」列、快览抽屉头部 tag、项目详情页头部 tag。筛选/排序/按钮可用性判定**继续用真实 `status`**（不参与 outcome 判定）。

## Consequences

- **变容易**：生态人员一眼分清「我自己撤销的」和「被商务驳回的」；驳回/撤销原因无需翻合同备注或连库；抽屉闭环了「这单到底经历了什么」，减少口头追问。
- **变难 / 代价**：
  - `bootstrap.logs` 全量下发（当前 715 条、随业务增长），抽屉过滤在前端做 —— 日志量级上去后需改为 `GET /projects/{id}/logs` 分页（照 PAGE-20261021 先例）。**记为技术债，本次不做**。
  - `time` 精度只到分钟（`now_str()`），同一分钟内多事件靠 `id` 排序保证顺序，展示上不区分秒。
  - 展示层多一套「终止细分」概念，必须在注释里写清「非状态机状态」，否则后续开发容易误以为后端有 `revoked` 状态。
- **可逆性：高**。全部是展示层 + 一个加性字段，回退 = 删 helper/区块 + 保留字段（加性字段留着无副作用）。

## 补遗（2026-10-22 实现期实测发现的三个边界）

### 补遗 1：`projectId` 复用导致时间线串台（**已在线上数据中发生**）
SQLite 的 `INTEGER PRIMARY KEY` 不带 `AUTOINCREMENT`，删除项目后 **id 会被复用**。实测：当前 `project id=2`（`SP-2026102216581487`，16:58 创建）的流转过程里混入了**已被删除的旧 project id=2**（13:56 删除）的 5 条日志，其中包括一条「删除项目 SP-2026102115254537」——时间线里出现别人的删除事件。

处置（两道）：
1. **前端 t0 守卫**：以本项目自身 `action='新增项目'` 日志的 `time` 作为起点，丢弃早于该时刻的日志（无该日志的存量单不限）。对当前数据有效（旧日志 13:56 < 新项目 16:58）。
2. **后端消除复用副作用**：`services.delete_project` 删除前把该项目全部日志的 `projectId` 置 `NULL`（日志文本、`targetName` 全部保留，审计不丢）。此后 id 即使复用，旧日志也不再指向新项目。
   - 副作用：这些日志对 viewer 变为不可见（`log_visible` 遇 `projectId IS NULL` 过滤）——但项目已删除，viewer 本就无法到达，可接受。

### 补遗 2：取数范围限定 `target='project'`
`add_log` 对 `target in ('project','outbound')` 都会写 `projectId`，交付单（outbound）日志将来也会带外键。本次**只取 `target='project'`**——交付信息已由「销售记录状态变更」日志覆盖，并入会重复；若后续要「交付单级」明细，另开条目。可逆。

### 补遗 3：存量日志 `projectId` 为 NULL（321 条中 307 条）
ADR-030 之前写入的项目日志没有外键，按 id 过滤会整片空态（真实存量单会「暂无流转记录」）。
处置：前端**兜底匹配** `target='project'` 且 `detail` 含本项目 `code`（`SP-` 编号全局唯一）的日志；仍为空则显示「暂无流转记录（存量项目无日志）」。**不按 `targetName`（项目名）匹配**——重名、改名都会串台。

### 补遗 4：撤销/驳回并存时的优先级
`projectOutcome` 固定 **撤销优先**。当前业务不可能同时出现（pending 单只能二选一，撤销后重新提交生成新项目），此处仅登记口径，防未来放开多次审核时出现歧义。

## 附：本次不改的东西
- `PROJECT_STATUS` 枚举与 `statusFilter` 选项（仍 5 项）
- 所有项目状态机守卫（ADR-012/026/028/032）
- `contracts.remark` 的写入格式（撤销/驳回仍按现有前缀写）
