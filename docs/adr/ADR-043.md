# ADR-043: 「重新提交」权限收紧为「下单人本人 + 管理员」，商务（editor）禁入

## Status
Accepted（2026-10-22，业务方明确要求「商务人员不能重新提交」）

## Context

1. **回填目标恒为下单人**（ADR-027 / `_withdraw_owner`：creator 优先，回退 rep）。因此：
   - 商务（editor）点击「重新提交」→ 明细进入**别人**的购物车，自己购物车毫无变化 → 用户视角是"点了没反应 / 提示成功但什么也没发生"；
   - 实测触发用户投诉：项目 creator 为 `lshangkun`，管理员/商务点击后收到「明细已回填至下单人 刘尚坤（lshangkun）的购物车，请通知该账号前往购物车改单」，而此刻**回填实际失败（`restored=0`，产品可售 0）** —— 提示把失败包装成了成功。
2. **提示掩盖失败另有独立缺陷**（ADR-042 补遗 6）：`decideRefillOutcome` 把「归属 ≠ 本人」置于分支最前，先于「全失败」判定，导致失败结果被归属文案吞掉。此缺陷与权限无关，必须单独修（否则管理员仍会看到同样的错误提示）。
3. 商务的合法改单路径本就存在：**通知下单人自己重新提交**，或由 admin 代为操作（admin 保留能力的理由是运维兜底）。

## Decision

### 1. 服务端权限：`viewer`（限本人项目）+ `admin`，`editor` → 403
`services.refill_project_cart` 的守卫链追加（位置：`viewer` 权限判定之后、`replace` 仅本人判定之前，**仍在任何写操作之前**）：
```python
if user.role == "editor":
    raise HTTPException(403, "商务人员不可使用『重新提交』，请通知下单人本人操作")
```
- `viewer`：保持现状（`user_sees_project` 校验，仅自己下单的项目）；
- `admin`：保留（代操作场景，回填目标仍是下单人，且 `mode=replace` 受「仅本人」限制 → admin 只能用 merge）；
- 路由 `require_order` **不改**（三个角色都能进端点，由上面这行做业务级拒绝，错误信息更准确）。

### 2. 前端入口：仅 `isAdmin || isViewer` 渲染
列表页与详情页的「重新提交」按钮 `v-if` 由 `(canWrite || isViewer)` 改为 `(isAdmin || isViewer)`。商务看不到任何入口（含禁用态），与其他"商务不可用功能直接不渲染"的既有口径一致。

### 3. 归属提示降级为「结果修饰」，不得掩盖失败（ADR-042 补遗 6）
分支顺序调整为：
1. `alreadyRefilled` → 已在购物车（若目标非本人，文案说明在谁的购物车）
2. `restored === 0` → **全失败弹窗**（标题下注明回填目标是谁）
3. `skipped > 0` → 部分成功：目标非本人 → 通知归属；本人 → 跳转 + 警告条
4. 全成功 → 目标非本人 → 通知归属；本人 → 跳转

## Consequences

- **变容易**：商务不再遇到"提示成功但什么也没变"；失败结果永远优先于归属文案；权限与业务语义（订单归属下单人）一致。
- **变难 / 代价**：
  - **商务彻底失去项目重提能力**：误建单/被驳回单只能由下单人自己操作或找 admin；
  - 若某商务实际承担"代客重下单"职责，流程需改为 admin 代做（本 ADR 不提供例外）；
  - `403` 是新增错误码，前端需正确处理（`showError` 已通用）。
- **可逆性：高**。回退 = 删掉那行 role 判断 + 前端 `v-if` 改回 `(canWrite || isViewer)`，无数据迁移。

## 附：与既有 ADR 的关系
- **部分取代 ADR-027 §权限**（原「admin/editor 放行」中的 editor 部分失效）；
- 不改变 ADR-042 的 `mode`、替换语义、`replace` 双守卫；
- 不改变撤销（withdraw）权限：viewer 本人 + 商务/管理员仍可撤销（另行口径）。
