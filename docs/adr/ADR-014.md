# ADR-014: viewer 只读拦截统一由后端权限守卫兜底，移除前端角色白名单

## Status
Accepted（2026-10-20）

## Context
BUG-20261020-#1：`frontend/src/api/index.ts` 的 axios 拦截器维护了一份 viewer 写请求白名单（仅购物车 + `/sales/order`），与后端 `require_order` 的放开范围（项目编辑/状态变更/合同状态/重新提交）不一致，导致 viewer 的编辑/取消/终止/交付/重新提交全部被前端拦截。两套权限清单已经漂移过一次。

## Decision
1. 删除前端 viewer 写请求白名单及拦截逻辑，所有写请求放行给后端判定。
2. 后端保持 ADR-009 的守卫模型：`require_order`（下单链路，含归属校验）/ `require_editor`（管理操作），services 层做资源归属校验（viewer 只能操作自己项目）。
3. 前端按钮的显隐/禁用继续按角色 + 归属渲染（`canOwn` 等），但仅作为 UX 提示，不作为安全边界。
4. 后端拒绝时统一返回 403，前端拦截器对 403 做统一 toast（含"只读账号"语义），替代原前端预拦截提示。

## Consequences
- 变容易：权限清单单一事实来源在后端；后续放开/收紧 viewer 权限只改一处；前后端联调不再因白名单遗漏静默失效。
- 变难：viewer 误点按钮时会真正发请求再收到 403（多一次网络往返）；要求后端每个写接口都有守卫（需自查一遍 api.py 路由依赖，不允许裸接口）。
- 可逆性：高。恢复前端白名单只是加回一段拦截器代码；后端守卫不动，安全边界不受影响。
