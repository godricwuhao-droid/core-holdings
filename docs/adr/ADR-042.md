# ADR-042: 「重新提交」回填购物车的三种缺陷修复（合并语义/失败动线/归属提示）

## Status
Accepted（2026-10-22，业务方确认：采纳「弹窗让用户选」+「合并=替换不累加」，并要求补充「已被占用/可售不足」说明）

## Context

「重新提交」= `POST /projects/{id}/refill-cart`（ADR-027）：把终止项目明细回填**下单人**购物车，前端跳 `/cart` 改单重提。实测发现三个缺陷：

### 缺陷 1：失败静默 + 往空车跳（"没有回到购物车"的直接原因）
实测数据：被驳回项目 `SP-2026102216581487`（`cartRefilled=0`）含 2 行明细，其产品（id 27/32）库存均为 1、`lockedQty=1`（被 pending 项目 4 锁走）→ **可售 0** → 两行全部跳过 → `cart_items` 零新增，但前端仍 `router.push('/cart')`。
用户落到**空购物车**，只看到一句「（2 行未能回填，请核对明细）」，既不知哪行失败、也不知为什么（`skippedReasons` 后端有返回，前端丢弃）。

### 缺陷 2：购物车非空时静默累加，且重试会翻倍
`_refill_cart_from_project` 走 `_cart_add_inner`，判重键 `(userId, assetId, itemId, customer)` 命中即 **数量累加**。
- 购物车已有同产品同客户行 → 回填后数量凭空变大，用户不知情；
- BUG-15 为支持重试，`skipped>0` 时 `cartRefilled` 保持 `False` → 用户再点一次 → 上次已成功行**再累加一次** → 数量翻倍。幂等标记是"整单布尔"，回填动作却是"逐行累加"，粒度不匹配。

### 缺陷 3：代操作归属错位
回填目标恒为**下单人**（`_withdraw_owner`：creator 优先，回退 rep）。admin/其他商务代点「重新提交」时，明细进了下单人的车，操作者自己跳 `/cart` 看到空车 —— 功能成功但无人可见。实测三个终止项目 creator 均为 `lshangkun`。

## Decision

### 1. 合并语义改为「同键替换」，不做累加
`_cart_add_inner` 增加可选参数 `existing_policy: "accumulate" | "replace"`，默认 `accumulate`（**加购行为零变化**：用户连点两次加购仍是 qty 累加）。
`_refill_cart_from_project` 传 `replace` → 命中同键行时**把 qty / amount / 服务期限覆盖为回填值**，不新增行、不累加。
- 顺带根治缺陷 2 的翻倍问题（重试幂等靠"替换"天然成立）。
- `withdraw_project`（撤销）同样复用该函数 → 撤销回填也变为替换语义（同键不再翻倍），日志文案不变。

### 2. 增加 `mode` 参数：`merge`（默认）| `replace`（清空后回填）
- `mode=merge`：保留购物车现有商品，同键行被覆盖，其余保留。
- `mode=replace`：**先清空下单人购物车**再回填（同一事务）。
- `mode=replace` **跳过 `cartRefilled` 幂等短路**（用户主动选择"清空重建"，此时幂等标记不构成理由；否则购物车被清空后明细永远回不来）。返回 `forced: true`。
- 非法 mode → 400。

### 3. 失败动线：`restored=0` 不跳转；部分成功跳转但显式警告
后端返回逐行结果 `rows: [{assetName, qty, ok, reason}]` + `owner: {id, username, name}` + `cleared`（replace 清掉的行数）+ `mode` + `forced`。
前端：
- `restored === 0` → **不跳 `/cart`**，弹窗列出每行 `reason`（标题「无法回填到购物车」）。
- `0 < restored` 且有跳过 → 跳 `/cart`，通过 `router.push({ state })` 传 `skippedReasons`，购物车顶部显示**可关闭的警告条**。
- 全部成功 → 跳 `/cart`，无警告条。

### 4. 可售不足的原因要说人话（业务方特别要求）
预检阶段直接产出带数值的原因，不再透传底层校验文案：
```
「融合视讯云平台」可售数量不足（库存 1，已锁定 1，已出库 0，本次需 1），
该产品已被其他订单占用，请等待释放或补货后再提交
```
- 预检在逐行回填**之前**做（`availableQty = quantity - lockedQty - shippedQty`），不可行行直接计入 `skipped` 并给出上述原因，不再进入 `_cart_add_inner`（避免抛出不含库存细节的泛化文案）。
- 区间不符等其他原因仍走原校验，`reason` 带产品名。

### 5. 归属提示
回填对象 ≠ 当前登录者时，前端提示「明细已回填至 下单人（姓名/账号）的购物车」并**停留原页**（不跳转），提示里给一句"请通知该账号前往购物车改单"。
- 语义不变（订单归属仍在下单人），仅把"回填到谁那儿"讲清楚。

## Consequences

- **变容易**：失败可解释（哪行、为什么、缺多少）；重试不再翻倍；购物车非空时用户有明确选择权；代操作不再"成功但看不见"。
- **变难 / 代价**：
  - `refill-cart` 响应结构扩展（`rows/owner/mode/forced/cleared`），前端需同步（**加性，不破坏旧字段**）；
  - `mode=replace` 会清空下单人购物车且**不可撤销**（弹窗必须显著警告）；
  - 回填语义由"累加"改"替换"，若有用户依赖"撤销后同键行数量叠加"的隐性行为，将不再成立（业务上不认为这是需求）；
  - 前端列表页与详情页两处「重新提交」需共用一套流程（新增 composable 或抽函数），否则两套动线必然漂移。
- **可逆性：中高**。语义变更（累加→替换）回退需改回 `existing_policy` 默认值；`mode` 与响应字段为加性，删除无副作用。数据已写入购物车的行为不可自动回滚（但购物车是临时态，影响可控）。

## 补遗（2026-10-22 实现期裁决的四个边界）

### 补遗 1：`mode=replace` **先预检、后清空**；可行行为 0 时**不清空**
原实现「先清空再逐行回填」+ 无条件 `commit` → 若全部行因可售不足被跳过，结果是**购物车被清空且无法回滚**（用户选了"清空后回填"，货没回来、原有商品也没了）。这是数据破坏级缺陷。
**裁决**：replace 必须两阶段——① 先做纯计算预检（不改任何数据），得出可行行集合；② `可行行数 == 0` → **跳过清空**，直接返回 `cleared=0` + 全量 `rows`（全 `ok=false`），由前端弹「无法回填」；③ 可行行数 > 0 → 才清空并只回填可行行（用户在选择时已被明确告知「将清空 N 项」）。
副作用：`cleared` 可能为 0 而 `mode=replace`，前端文案不得假设"已清空"。

### 补遗 2：`mode=replace` **只允许清空自己的购物车**
回填目标恒为**下单人**（ADR-027/026 口径）。若操作者是 admin/其他商务，`replace` 会清空**他人**购物车 —— 跨用户破坏，不可接受。
**裁决**：`mode=replace` 且 `target_user_id != str(user.id)` → `400「只能对本人购物车执行『清空后回填』，他人项目请使用合并」`。代操作场景仅保留 `merge`（同键覆盖仍生效，不会翻倍）。

### 补遗 3：`alreadyRefilled` 优先级高于「全失败」
`mode=merge` 命中幂等短路时后端返回 `alreadyRefilled=true, restored=0, rows=[]`。若按 §3 字面「`restored===0` → 弹无法回填」，会把「明细已在购物车」误报为失败。
**裁决**：前端分支顺序固定为 **① 归属提示 → ② `alreadyRefilled` → ③ `restored===0` 全失败 → ④ 部分失败 → ⑤ 全成功**。此顺序不得调整。

### 补遗 5：幂等短路 + 本人空车 → 自动改走 `replace` 重填一次
真实数据可复现：项目 `SP-2026102217033828`（`cartRefilled=1`）的下单人购物车为空 → `mode=merge` 命中短路返回 `alreadyRefilled=true` → 前端提示「明细已在购物车」并跳 `/cart` → **又是空车**（原始抱怨的第二条成因）。
**裁决**：同时满足 ①`alreadyRefilled=true` ②`cartCount === 0` ③回填对象为本人（`owner` 缺失视为本人）→ 前端**自动**以 `mode=replace` 再请求一次（**仅一次，无循环**），用第二次响应走既有结果分支。
安全依据：`replace` 已有服务端双守卫（补遗 2 仅限本人 + 补遗 1 可行行 0 不清空），且「本人 + 空车」下清空本身就是空操作。
若第二次请求失败（旧后端不认 `mode` / 归属判为他人 400 / 网络）→ **静默回退**首次响应的「已在购物车」分支，不向用户抛错，仅 `console.warn` 留痕。
- 补充约束：车里有货时**绝不**自愈（清空必须由用户显式选择），所以自愈路径永远不会弹三选框。

### 补遗 6：归属提示**不得掩盖失败**（原补遗 3 的顺序是错的）
原顺序「① 归属提示 → ② alreadyRefilled → ③ 全失败 → …」有致命缺陷：只要回填对象不是当前登录者，就直接返回「明细已回填至 X 的购物车」——**哪怕 `restored=0`、一行都没回填**。实测：商务点被占用产品，收到"成功"提示，实际全部失败。
**裁决**：归属从「最高优先级分支」降级为「结果修饰」，新顺序固定为：
1. `alreadyRefilled` → 已在购物车（目标非本人时说明在谁的购物车）
2. `restored === 0` → **全失败弹窗**（可注明回填目标是谁）
3. `skipped > 0` → 部分成功：目标非本人 → 通知归属；本人 → 跳转 + 警告条
4. 全成功 → 目标非本人 → 通知归属；本人 → 跳转

### 补遗 4：已知边界（本次接受，不改）
- **归属预判是启发式**：前端弹「三选」之前只能按 `creator`（空则 `rep`）推断回填目标，权威 `owner` 在响应里。极端情况（`creator` 为空且 `rep` 指向他人）会为他人车弹框 —— 但补遗 2 已使 `replace` 在服务端被拒，最坏结果退化为 400 提示，不再破坏数据。
- **警告条不持久**：购物车页读完 `history.state.refillSkips` 即清空，刷新后丢失（未回填明细仍可在项目详情「流转过程」查）。接受，不引入 sessionStorage/新表。
- **重试循环未加记忆**：部分失败后再次点击仍会重新询问模式。接受（补遗 1/2 已消除破坏性后果）。

## 附：本次不改
- `cartRefilled` 仍为整单级布尔（不引入行级回填记录表）——替换语义已消除重复累加，无需新表。
- 不改 `POST /cart` 加购语义（累加仍保留）。
- 不改撤销（withdraw）的日志文案与流转事件。
